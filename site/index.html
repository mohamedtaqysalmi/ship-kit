Workflows I copy into client repos, with the ways they fail written down.

Every small project ends up needing the same pipelines: checks on pull requests, a Docker image, a release, a deploy that can roll back, a database backup. I wrote these as single files you copy, each with its required secrets and failure modes. None of them has been run in a real repo yet, and each one is labelled that way until a real run is linked.

    What works

    This is what I can say about all six today, and what I cannot.

    • works This repository's CI lints every file under workflows/ with actionlint and yamllint on each pull request.
    • works Actions are pinned to full commit SHAs, and each job sets its own permissions:.
    • partial The failure modes in each README come from reading the tools' documentation and the scripts, not from watching the workflows fail.
    • not run No workflow has been run in a real repo. Each has a note under docs/evidence that says what a real run needs.

    Quickstart

    Copy the YAML from the picker into .github/workflows/ in your repo, set the secrets its README lists, and push. For example, the PR checks: 

    mkdir -p .github/workflows
curl -fsSL -o .github/workflows/pr-checks-node.yml \
  https://raw.githubusercontent.com/mohamedtaqysalmi/ship-kit/main/workflows/pr-checks-node/pr-checks-node.yml
git add .github/workflows/pr-checks-node.yml

    How it is laid out

    Each workflow is a folder. The picker and the repository read the same files, and a check fails the build if the catalog and the folders disagree. 

    workflows/
  <name>/
    <name>.yml     the file you copy
    README.md      secrets, setup, failure modes
docs/evidence/
  <name>.md       real run link, or what is still missing
site/
  snippets/        copied from workflows/ at build time

    How I built it

    Evidence before the word "tested"

    A workflow only counts as tested when a real run is linked from docs/evidence/. Until then, every place that lists it says it has not been run.

    The release workflow uses the gh CLI

    The runner already has gh, so the release job calls gh release create instead of pulling in a third-party action I would have to trust and keep pinned.

    Permissions per job

    Workflows default to contents: read. The one job that pushes to GHCR or creates a release asks for the extra scope itself.

    Limits and roadmap

    • Real runs are the missing piece. Without them these are reviewed files, not proven ones.
    • The Python and Node checks assume a conventional layout: a root package.json or requirements.txt.
    • SSH deploy assumes a Linux host with rsync and a release directory I describe in its README.

    Open work is in the issues. To report a bug or add a workflow, start with CONTRIBUTING.md.
