# release-from-tag

Creates a GitHub Release with generated notes when a tag matching `v*` is pushed. Tags containing a hyphen, such as `v1.2.0-rc.1`, are marked as pre-releases.

**Status: not yet run in a real repo.** No evidence exists in `docs/evidence/` yet, so treat this as untested.

## Use it

Copy `release-from-tag.yml` to `.github/workflows/` in your repo, then push a tag:

```bash
git tag v1.0.0
git push origin v1.0.0
```

The release is created with the GitHub CLI (`gh release create`) that is already on the runner, so there is no third-party action to pin. The tag name is passed through an environment variable rather than interpolated into the script.

Release notes are generated by GitHub from merged pull requests since the previous tag. You can tune the categories with a `.github/release.yml` file in your repo.

## Required secrets

None. It uses the built-in `GITHUB_TOKEN`. Only the `release` job has `permissions: contents: write`.

## Failure modes

- **`HTTP 403: Resource not accessible by integration`.** The repo or organization restricts workflow permissions in a way that blocks the job's `contents: write`. Check Settings, Actions, General.
- **`release already exists`.** The tag already has a release, for example because you pushed it twice or created the release by hand. Delete the release and re-run, or use a new tag.
- **Tag does not exist.** The command runs with `--verify-tag`, so it fails instead of creating a tag on its own.
- **Thin notes.** Generated notes are built from pull requests. Commits pushed straight to the default branch show up less clearly.
- **Nothing happens when you push a tag.** The tag must match `v*`. Tags created by another workflow using `GITHUB_TOKEN` do not trigger workflow runs.
- **No build artifacts.** It only creates the release. Add a build step and `gh release upload` if you need assets.
